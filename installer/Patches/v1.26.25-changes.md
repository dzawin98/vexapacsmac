# VEXAPACS-RIS V1.26.25 — Worklist cepat (akar masalah: DDL per permintaan)

Berisi seluruh perbaikan V1.26.23 + V1.26.24 + memoisation skema. Pakai versi ini.

## Akar masalah kecepatan worklist

Diukur per tahap pada endpoint sungguhan, dan hasilnya membantah semua dugaan awal
(indeks, gzip, SQL):

| Tahap | Waktu |
|---|---|
| `SELECT 1` (pool round trip) | 0,4 ms |
| query data worklist yang sebenarnya | 2,0 ms |
| endpoint `/api/system/health` | 0,9 ms |
| **`GET /api/mwl/orders`** | **211–299 ms** |

Penyebabnya: `ensureMwlTables()` dijalankan pada **setiap** permintaan dan menjalankan
**~80 statement DDL** — 6× `CREATE TABLE IF NOT EXISTS` + **58× `ALTER TABLE ... ADD COLUMN
IF NOT EXISTS`** + 12 perubahan skema pasien + 4 pembuatan indeks. Semua untuk memeriksa skema
yang tidak bisa berubah selama service berjalan.

**Perbaikan:** dijalankan sekali per proses lalu diingat. Kegagalan TIDAK di-cache, jadi kalau
database sempat mati, permintaan berikutnya mencoba lagi dan tidak terjebak permanen.

### Hasil terukur

| Endpoint | Sebelum | Sesudah |
|---|---|---|
| worklist 1000 baris | 299,2 ms | **4,7 ms** |
| worklist 10 baris | 211,4 ms | **3,6 ms** |
| worklist + filter tanggal | 210,8 ms | **3,6 ms** |

**±64× lebih cepat.** Diverifikasi isinya utuh: 200 OK, JSON valid, 85 kolom per baris,
7.281 byte — tidak ada kolom yang dibuang. Setelah restart, 6 tabel dan 10 indeks
`mwl_orders` tetap lengkap.

## Filter tanggal — dua bug, sekarang diperbaiki

### Bug 1: HTTP 500 pada setiap permintaan bertanggal
`CAST(? AS date) + INTERVAL 1 DAY` tanpa tanda kutip adalah **syntax error** di PostgreSQL.
Setiap permintaan dengan `dateMode` mengembalikan 500. Diganti `+ 1` (bentuk valid untuk
tanggal) dan diuji langsung ke database.

### Bug 2: "pilih Today tapi semua tetap muncul"
Tabel worklist **bukan** berasal dari RIS. Ada dua sumber yang digabung:

| Sumber | Endpoint | Isi |
|---|---|---|
| PACS QIDO | `/rs/studies` | tabel utama (baris dari modality) |
| RIS order | `/api/mwl/orders` | hanya order yang belum dikirim ke PACS |

Filter tanggal sebelumnya hanya dipasang di RIS, sehingga tidak menyentuh baris PACS sama
sekali. Sekarang rentang dikirim ke **PACS** sebagai `StudyDate` (format DICOM:
`YYYYMMDD` atau `YYYYMMDD-YYYYMMDD`) sekaligus ke RIS.

Diverifikasi dengan memanggil `queryPacsMetadata()` dari build PACS secara langsung:

| Filter | Hasil |
|---|---|
| tanpa filter | 21 record (2025–2026) |
| `20260702` | 2 record, hanya tanggal itu |
| `20260101-20260630` | 12 record, semua dalam rentang |
| `20260919` (tanpa pemeriksaan) | 0 record |
| `20260701-20260731` | 3 record |

Penyaringan memakai **StudyDate** (tanggal pemeriksaan). Konsekuensi yang perlu diketahui:
order yang dibuat hari ini tetapi diperiksa besok tidak muncul pada filter "Today".

Pengaman tambahan: bila index metadata PACS tidak tersedia, PACS jatuh ke C-FIND yang mungkin
tidak menghormati rentang — baris tanpa tanggal kini dibuang saat filter tanggal aktif.

## Opsi "All dates" dihapus

Pilihan tersisa: Today, Yesterday, Last 7 days, Last 30 days, 1 Month, 2 Month, Custom range.
Ada juga parameter `offset` di endpoint untuk pagination server.

## Indeks (juga berlaku untuk instalasi lama)

`idx_mwl_orders_created_at`, `idx_mwl_orders_deleted_created`, `idx_mwl_orders_updated_at`,
`idx_mwl_logs_order_active`.

`CREATE TABLE IF NOT EXISTS` tidak menyentuh tabel yang sudah ada, jadi instalasi lama tidak
akan pernah menerima indeks baru lewat cara itu. Ditambahkan `ensureMwlOrderIndexes()` yang
menambahkan indeks secara idempoten.

Terukur pada PostgreSQL 18 dengan 200.000 baris, query identik dengan yang dihasilkan server:
**0,16 ms** dengan indeks (Index Scan Backward, 300 baris, 302 buffer) vs **20,0 ms** tanpa
indeks (Seq Scan 200k + top-N sort, 1088 buffer) — ±125×.

Begitu pula `LIMIT`: 1000 baris = 2,97 ms vs 100 baris = 0,07 ms (42×), karena layar hanya
menampilkan 100 baris sementara aplikasi meminta 1000.

## Kompresi

| | Ukuran |
|---|---|
| tanpa kompresi | 7.281 B |
| gzip | 1.497 B |
| Brotli | 1.410 B |

Brotli hanya **5,8% lebih kecil dari gzip** — bukan perbaikan besar. Yang lebih berarti:
kompresi kini di-cache, karena sebelumnya zlib dijalankan pada setiap respons termasuk payload
auto-refresh 30 detik yang byte-nya identik.
