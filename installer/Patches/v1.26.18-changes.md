# VEXAPACS-RIS V1.26.18 — Perbaikan

## 1. Export Video (Cine → MP4/AVI/MPEG) — ffmpeg tidak pernah ikut installer
Penyebab sebenarnya bukan codec: `DESKTOP VIEWER SSR/server/exportRuntime.mjs` memanggil
`spawn(process.env.FFMPEG_PATH || 'ffmpeg')`, tetapi installer tidak pernah memaket ffmpeg.
Preview (webm/vp9) jalan di browser; MP4/AVI/MPEG gagal di langkah encode server.

- `installer/vendor/fetch-ffmpeg.ps1` — unduh build portable (URL paket langsung; URL
  `ffmpeg-release-essentials.zip` menghasilkan unduhan terpotong).
- `prepare-payload.ps1` — salin ke `payload/app/PRIMARY VIEWER/tools/ffmpeg/`
  (pakai `Copy-Item`, BUKAN `Copy-Project`: yang terakhir selalu membuat direktori).
- `vexapacs-ris.iss` — baris `[Files]` eksplisit + `Excludes: ffmpeg,ffmpeg\*` pada
  `vendor\*`, supaya binary 103 MB tidak ikut dua kali.
- `install-services.ps1` — set `FFMPEG_PATH` pada service `VexaDesktopViewer`.
- `exportRuntime.mjs` — `resolveFfmpegBinary()` (FFMPEG_PATH → tools/ffmpeg → cwd →
  VEXA_FFMPEG_DIR → PATH) dan pesan error yang jelas untuk ENOENT/-4058.
  `GET /api/viewer/dicom-print` kini melaporkan `ffmpegAvailable` sesungguhnya.

Diverifikasi pada payload hasil paket: resolver menemukan binary bawaan tanpa PATH dan
tanpa `FFMPEG_PATH`; ketiga format berhasil di-encode (libx264 / mjpeg / mpeg2video).

## 2. Worklist Technologist Lemot — dua penyebab
- **Agregat tabel penuh.** `LEFT JOIN (SELECT order_id, MAX(is_active) FROM mwl_logs
  GROUP BY order_id)` memaksa scan seluruh `mwl_logs` sebelum `ORDER BY ... LIMIT`.
  Diganti `LEFT JOIN LATERAL` (pakai `idx_mwl_logs_order`), dipakai di 3 query
  (list, update, restore). Terukur pada 150k order: **747 ms → 70 ms**, hasil identik.
- **Tidak ada kompresi respons.** Backend tidak punya middleware gzip; worklist
  649 KB mentah, di-poll tiap 30 detik. Ditambah wrapper gzip pada `res.json`:
  **649 KB → 35 KB (18x)**.

## 3. Sinkronisasi Data Otomatis (baru)
Endpoint server-only (menolak non-loopback, HTTP 403) di RIS backend:
- `POST /api/system/sync/pacs` — baca ulang seluruh folder DICOM → rebuild
  `pacs_instances`/`pacs_series`/`pacs_studies`.
- `POST /api/system/sync/ris` — rekonsiliasi `mwl_orders` (SENT_TO_MWL → COMPLETED)
  dijalankan sampai habis, bukan throttle 200 baris / 30 detik.
- `POST /api/system/sync/all` — keduanya berurutan (PACS dulu, baru RIS).

Tombol **"Sync All Data"** di `tools/service-monitor` (Vexa System Utility) →
tab **Diagnostics & Recovery**, di samping "Run Preflight Check". Menampilkan hasil
per-langkah; port RIS dibaca dari env service `VexaRISBackend`.

Catatan: ini **bukan** sinkronisasi RIS↔PACS dua arah. Yang ada: file DICOM → metadata
PACS (otomatis & manual), lalu status order RIS direkonsiliasi dari keberadaan study
di PACS. Nama DB yang benar adalah `veloris_db` dan `velopacs_db`.
