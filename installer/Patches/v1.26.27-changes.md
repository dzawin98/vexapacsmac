# VEXAPACS-RIS V1.26.27 — Export MP4 jalan, viewer tidak lagi blank

Berisi seluruh perbaikan V1.26.26 + perbaikan di rilis ini.

## 1. Export MP4/AVI/MPEG selalu gagal — akar masalah: URL kurang prefix `/viewer`

Keluhan: "error encoding, gabisa export tapi di preview bisa". Preview jalan, export gagal —
asimetris itu justru petunjuknya: **preview dirender 100% di browser** (MediaRecorder),
sedangkan MP4/AVI/MPEG dikirim ke server untuk di-transcode ffmpeg. Hanya jalur server yang rusak.

Terukur langsung pada instalasi produksi (192.168.19.110):

| Permintaan | Hasil |
|---|---|
| `POST /api/viewer/export/video` (yang dikirim aplikasi) | **404** `text/html` — `Cannot POST /api/viewer/export/video` |
| `POST /viewer/api/viewer/export/video` (jalur benar) | 500 JSON berisi pesan ffmpeg |
| `GET /api/viewer/dicom-print` | **404** |
| `GET /viewer/api/viewer/dicom-print` | 200 + `ffmpegAvailable: true` |

Penyebabnya: aplikasi mengirim permintaan ke `/api/viewer/...`, sedangkan Caddy memetakan
`/api/*` ke RIS backend (3001) dan tidak punya aturan `/viewer/api/viewer/*`. Jadi permintaan
keluar dari aplikasi viewer dan mendarat di server RIS, yang memang tidak punya route itu → 404.
Kode yang benar sudah ada (`appUrl()` menambahkan prefix), hanya 4 pemanggilan yang terlewat:

- `exportCenter.ts` → `transcodeVideo` (MP4/AVI/MPEG), `loadDicomPrintSettings`, `sendDicomPrint`
- `DicomPrinterConfigPanel.tsx` → load + simpan konfigurasi printer

Artinya selain MP4, **DICOM Print dari viewer juga mati di produksi karena bug yang sama** —
sekarang keduanya diperbaiki.

Diperiksa di server produksi: `ffmpegAvailable: true`,
`ffmpegPath: C:\Program Files\VEXAPACS-RIS\PRIMARY VIEWER\tools\ffmpeg\ffmpeg.exe`.

## 2. Viewer kadang terbuka blank

Dua sebab berbeda, keduanya diperbaiki.

### 2a. Blank hitam permanen tanpa pesan apa pun

`ViewerDeepLinkLoader` merender `<main className="launch-blank-page">` ketika tidak ada pesan
error, dan kelas CSS itu berisi `background: #050505` — layar hitam penuh. Akibatnya, ketika
pemuatan studi gagal sesaat (mis. PACS/DICOMweb timeout sesaat), yang terlihat persis seperti
keluhan: tab terbuka, hitam, tanpa teks, dan **tidak pernah pulih** karena tidak ada percobaan
ulang.

Perbaikan:
- Bila daftar series kosong, kode sekarang membedakan **studi benar-benar kosong** (terminal)
  dari **kegagalan permintaan** (sementara), dengan memanggil ulang `getStudy()` sebagai
  konfirmasi. Hanya kasus sementara yang diulang.
- Percobaan ulang otomatis dibatasi (`MAX_AUTO_RETRIES = 2`) dengan jeda bertingkat, jadi tidak
  ada loop tanpa akhir.
- Pesan masih tampil di layar (tidak lagi blank) dan sekarang ada tombol **Reload** di sebelah
  tombol tutup, supaya operator selalu punya jalan keluar tanpa harus tahu caranya.

### 2b. Peringatan "Too many active WebGL contexts" dan citra hilang

Terukur pada browser sungguhan yang membuka viewer di produksi:

| Pengukuran | Hasil |
|---|---|
| `navigator.hardwareConcurrency` | 16 → konfigurasi lama meminta **8** context |
| Context WebGL dibuat satu viewport stack | **11**, 2 langsung dicabut |
| `webglcontextlost` saat kuota dipaksa penuh | **26** kehilangan |
| Kuota Chrome per proses renderer | ±16 |

`WebGLContextPool.js`: **setiap `new RenderingEngine(id)` membuat pool SENDIRI** sebanyak
`webGlContextCount`. Jadi 8 context per engine — satu viewport stack ditambah satu pane MPR/3D
sudah melewati kuota. Chrome lalu mencabut context terlama
(`Too many active WebGL contexts. Oldest context will be lost.`) dan **tidak pernah
memulihkannya**: tidak ada penanganan `webglcontextlost`/`webglcontextrestored` sama sekali di
`@cornerstonejs/core` 5.1.4 (diperiksa dengan grep), dan Chrome tidak memicu `restored` untuk
context yang di-evict. Context mati permanen, draw berikutnya jadi no-op — viewport melaporkan
render sukses sementara layar kosong.

Perbaikan:
- Ukuran pool diturunkan dari 8/7/5/3 (berdasar jumlah core) menjadi **4 per engine**, tetap
  bisa dioverride lewat `VITE_CORNERSTONE_WEBGL_CONTEXTS`.
- Modul baru `webglContextWatch.ts`: mengubah spam peringatan menjadi **satu pesan yang bisa
  ditindaklanjuti**, mendengarkan `webglcontextlost` (tanpa `preventDefault`, supaya kehilangan
  tidak disamarkan), disambungkan di `DicomViewport` dan `ViewerShell` sehingga operator dapat
  pesan + tombol Reload alih-alih tile kosong tanpa penjelasan.

Catatan jujur: context yang sudah dicabut **tidak bisa** dipulihkan di tempat (resource GPU sudah
hilang dan Chrome tidak memulihkannya). Karena itu mitigasinya adalah pool lebih kecil + pesan
jelas + Reload — bukan klaim pemulihan otomatis.
